# Корпоративная сеть и пилот MikroTik

Сведения собраны из переписки, локальных материалов и исторического экспорта RouterOS от 11 ноября 2026 года. Текущий VPN сотрудников работает как отдельный VPS. Внедрение прозрачного шлюза на MikroTik этими проверками не подтверждено.

## Подтверждённые зависимости

- Внутренняя RU-VM имела адрес `10.10.21.37`. Этот адрес доступен только при наличии корпоративного маршрута. Он не подходит как универсальная публичная точка входа для телефона вне сети.
- Исторический VLESS-вход VM слушал TCP `41686`. На MikroTik применялся dst-nat публичного TCP-порта на VM с разрешением соответствующего трафика в `forward`. Рабочая доступность была подтверждена пользователем. Публичные адреса офиса следует брать из действующей конфигурации WAN, поскольку в переписке фигурировали разные адреса.
- Для доступа из LAN к собственному публичному адресу могут потребоваться split DNS либо hairpin NAT. Изменение адреса в панели 3x-ui меняет выдаваемую ссылку, но само по себе не создаёт dst-nat и правила firewall.
- `portal.parkskazka.com` на корпоративном ПК разрешался в `10.10.21.24`, трасса проходила через `10.10.3.1`. Это подтверждает системный DNS и ICMP-маршрут на этом ПК, но не HTTPS-соединение через прокси.
- В материалах корпоративные DNS указаны как `6.6.20.10` и `6.6.20.20`. Диапазон `6.6.0.0/16` не относится к RFC 1918. Автоматическое правило `geoip:private` не заменяет явных маршрутов к корпоративным DNS и другим нестандартным префиксам.

## Почему direct на сервере не заменяет direct на ПК

В тестере RU-панели домен `portal.parkskazka.com` выбирал `direct`, а IP `10.10.21.24` выбирал `blocked`. Тестер показывает решение маршрутизатора Xray без передачи запроса. Если клиент уже отправил IP, доменное правило может не сработать. Кроме того, `direct` сервера означает исходящее соединение самого сервера. VPS за пределами компании обычно не имеет маршрута к её частной сети.

В текущем полном клиентском JSON корпоративный домен и нужные IP направляются в клиентский `direct`, выше общего `proxy`. Для корпоративной зоны используется системный DNS Windows. Удалённому сотруднику всё равно нужен действующий корпоративный VPN и маршруты к внутренним ресурсам. Дублирование тех же правил на Исландии такую связность не создаёт.

## Требования к будущему пилоту

Пользователь выбрал IT VLAN, LAN и корпоративный Wi-Fi. При отказе цепочки обычный интернет должен сохраняться. Гостевые сегменты автоматически в пилот не включаются.

Рассматривались локальный WireGuard от MikroTik к RU-VM/Xray и контейнер Xray на RouterOS. Локальный WireGuard внутри корпоративной сети не проходит через внешний DPI провайдера. Если же WireGuard вынести на публичный участок, его внешний протокол и свойства обнаружения становятся отдельным вопросом.

Перед внедрением нужны проверка модели и архитектуры MikroTik, поддержки контейнеров, ресурсов, MTU, пропускной способности, двух WAN, существующего AWG, FastTrack, mangle и симметрии ответов. Полный fail-open требует проверки доступности интернета именно через Xray, поскольку живой интерфейс или ping шлюза не подтверждает работоспособность внешнего VPN. Надо заранее исключить из перенаправления адрес внешнего сервера, управление, корпоративные сети и DNS, иначе возможна петля.

Практический порядок — отдельный тестовый ПК, отдельная таблица маршрутизации, явные исключения, проверка TCP/UDP и DNS, затем искусственное отключение Xray и проверка возврата на WAN. После этого расширять список источников. Готовых правил RouterOS для применения вслепую в этом репозитории нет. Исходный экспорт и прежний обзор сохранены в исключённом из Git `local/mikrotik/`.
