# Windows, VPS и 3x-ui

## Выдача профиля Windows

1. Создайте отдельного клиента в нужном inbound 3x-ui и скопируйте его VLESS-ссылку.
2. Откройте `tools/employee-profile-generator/Create-Profile.cmd` и укажите имя файла. Если в буфере нет ссылки, вставьте её по запросу. Результат появится в `profiles/` рядом с генератором.
3. В v2rayN импортируйте полный JSON как **Custom**, выберите ядро **Xray**, оставьте поле **Socks port** пустым и включите **Set system proxy**. Локальный mixed-прокси уже задан в JSON на `127.0.0.1:10808`.
4. Проверьте открытие корпоративного портала, браузерный трафик через VPN и прямой маршрут для российских ресурсов. Используйте ссылку, выданную этому сотруднику. Имя файла не влияет на UUID. Срок действия и отзыв доступа задаются в 3x-ui.

Генератор переносит транспорт из VLESS-ссылки или полного клиентского JSON. Комплект от 25 ноября поддерживает расширенные параметры XHTTP. При наличии Xray генератор проверяет конфигурацию перед сохранением. Путь к ядру можно передать через `-XrayPath`, а полный экспорт v2rayN — через `-SourceFile`. Для правил по геобазам нужны `geosite.dat` и `geoip.dat`.

## Маршрутизация Windows

- `parkskazka.com` с поддоменами направляется через `direct` и разрешается системным DNS Windows через `localhost` с `finalQuery`. Для внутренних адресов требуется доступ к корпоративной сети и её DNS.
- Российские домены, российские IP и частные назначения идут напрямую по соответствующим правилам. Для остальных назначений используется `proxy`.
- DNS-правила стоят выше общего маршрута. Настройки DNS в браузере или приложении могут влиять на разрешение имён, поэтому проверяйте портал в самом приложении.
- JSON из `configs/routing/` импортируются в редактор маршрутизации v2rayN для обычного профиля. Для **Custom** маршруты уже заданы в полном Xray JSON.
- При диагностике проверьте, какой конфиг использует запущенное ядро. В ноябрьской проверке UI показывал `RU-entry`, пока старый процесс Xray фактически работал через прямой профиль Reykjavík. Проверяйте внешний адрес и изменение счётчиков нужного inbound после переподключения.

## Проверка VPS и REALITY

На 25 ноября Xray `26.7.28` слушал TCP `443`, служба `x-ui` была активна, а панель слушала loopback. Клиентский Xray был версии `26.11.9`. Обновление серверного ядра обсуждалось. Выполнение обновления источники не подтверждают.

В отчёте аудита для `in-443-tcp` указаны VLESS, XHTTP и REALITY. TLS-цель была `telia.lt:443`, разрешённый SNI — `telia.lt`. В XHTTP зафиксированы host `lanet.ua`, путь `/api/v1/updates`, режим `stream-one`, метод `PUT` и padding `1000–4000` с размещением в cookie. Совпадение открытого ключа клиента с закрытым ключом сервера подтверждено. Отчёт показывал восемь ShortID с длинами от 2 до 16 шестнадцатеричных символов и без пустого значения. Полный серверный экспорт этого VPS среди найденных файлов отсутствует.

```sh
systemctl is-active x-ui
ss -lntp '( sport = :443 or sport = :47548 )'
timedatectl show -p NTPSynchronized
python3 audit-reality.py --client-sni telia.lt
```

Скрипт читает конфигурацию работающего Xray и выводит параметры REALITY, наличие закрытого ключа и статистику ShortID. Для сверки пары ключей передайте клиентский открытый ключ через `--client-public-key`. При ручной проверке PowerShell-профиля используйте `xray run -test -config <profile.json>`, затем проверьте передачу данных через выбранный прокси.

25 ноября проверены TLS 1.3, ALPN `h2` и имя сертификата для `telia.lt`. HTTP-цепочка `telia.lt` → `www.telia.lt` → `/privatiems` дошла до `200 OK`. Тестовый профиль Windows получил около 2,36 МБ, повторный запрос с принудительным маршрутом через VLESS также получил `200 OK`. Один тест с Windows выполнялся с `--ssl-revoke-best-effort` при недоступной проверке отзыва. Проверка имени и доверия оставалась включённой. Эти результаты относятся к проверенному ПК и моменту проверки.

## Доступ к панели

Используйте [комплект запуска](../tools/admin/README.md). Скопируйте `admin.example.json` в исключённый из Git `admin.local.json` и заполните проверенные адрес, URL и отпечаток. Оригинал комплекта с рабочими параметрами сохранён в `local/admin/local-install/`.

Скрипт запускает SSH-проброс на `127.0.0.1:47549` к порту панели `47548` и открывает Chrome с отдельным профилем. При первом подключении сверяйте отпечаток SSH с доверенным источником. Скрипт печатает путь к журналу SSH, который помогает различить отказ входа и невозможность поднять локальный порт. Пароль SSH вводится в окне SSH, пароль панели — в браузере.

### Если SSH завершился с кодом 255

Код 255 сам по себе не определяет причину. Сначала прочитайте журнал, затем проверьте `Test-NetConnection <server> -Port 22` на Windows. Доступный TCP-порт не подтверждает успешный вход.

В ноябре после трёх ошибочных паролей предполагалась блокировка Fail2ban. В показанном списке были два заблокированных адреса, принадлежность которых офису не подтверждена. Отключать защиту на основании этого вывода не требуется. С консоли провайдера или другого доступного SSH-сеанса проверьте конкретный jail и журнал.

```sh
fail2ban-client status
fail2ban-client status sshd
journalctl -u ssh --since '-15 minutes' --no-pager
```

Только если в списке находится подтверждённый текущий внешний IP администратора, выполните `fail2ban-client set sshd unbanip <verified-admin-ip>`. Для сотрудников предпочтительны отдельные SSH-ключи и отдельные учётные записи с разрешённым пробросом панели. Их создание и отключение парольного входа в этой работе не выполнялись.
