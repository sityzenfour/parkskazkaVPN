# ТСПУ, DPI и варианты развития

Состояние обзора на 25 ноября 2026. Исходная работающая схема сотрудников использует VLESS + XHTTP + REALITY на TCP 443. Панель доступна через SSH-проброс. Проверенные результаты текущего узла приведены в [отчете аудита](reality-audit-2026-11-25.md).

| Сигнал | Что получает наблюдатель |
| --- | --- |
| Сеть сотрудника | IP назначения, порт, объемы, направления и длительность, доступные признаки TLS и SNI |
| Сеть хостинга | Потоки между клиентами, VPS и внешними назначениями, сведения о выделенном сервере |
| Внешний ресурс | IP выхода и данные собственного соединения пользователя с этим ресурсом |
| Приложение устройства | Может дополнительно проверять состояние системного VPN и запрашивать внешний IP |
| Сканер входного адреса | Внешний ответ сервера при выбранных SNI, TLS и HTTP-запросах |

Путь XHTTP, метод PUT и cookie передаются внутри защищенного соединения. TLS-отпечаток и статистика пакетов остаются отдельными признаками. Работа ACM IMC 2022 описывает наблюдаемое состояние ТСПУ, а FOCI 2026 уточняет историю выборочной фильтрации QUIC по SNI. Наличие шифрования не устраняет решения по адресу и метаданным. [ACM IMC](https://censoredplanet.org/assets/tspu-imc22.pdf), [FOCI 2026](https://petsymposium.org/foci/2026/foci-2026-0010.php), [метаданные транспорта](https://www.rfc-editor.org/rfc/rfc9065.html)

1. **Что подтверждают замеры**

В исходном freeze-check за 5–6 ноября проверялись 435 доступных из контрольной точки файлов у 154 компаний. Из домашней сети 378 загрузок завершились, 52 начались и остановились, пять точек не ответили. Повтор 23 ноября из офисной сети в Тюмени дал 430 полных загрузок, пять без ответа и ноль зарегистрированных зависаний. Выбор входа требует проверки из сетей сотрудников и загрузки данных, помимо проверки соединения с портом. [Методика и данные](https://github.com/MarkSinD/freeze-check/blob/main/REPORT.md), [офисный повтор](https://github.com/MarkSinD/freeze-check/issues/15)

В Xray `26.11.9` изменен отпечаток `chrome` на Chrome 155+. Автор GitHub-обсуждения подтвердил работу релиза с мобильной сети на двух серверах. Это основание сравнить отдельный профиль `chrome` с действующим `firefox`. Изменения клиентского ядра определяют конкретный отправленный отпечаток. При явном `firefox` обновление серверной панели не переключает клиента на `chrome`. [Релиз](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9), [измерения пользователя](https://github.com/XTLS/Xray-core/issues/7131)

2. **Мосты и разные IP**

TCP-мост через NGINX stream или HAProxy может передавать поток REALITY к текущему VPS. Абонентский оператор видит адрес посредника. TLS-байты клиента остаются в проходящем потоке. На выходе сохраняется IP основного VPS, а обычный TCP-прокси меняет видимый серверу адрес источника на адрес моста. При внедрении нужно проверить per-IP лимиты, учет и доступность обоих участков. [NGINX stream](https://nginx.org/en/docs/stream/ngx_stream_proxy_module.html), [HAProxy TCP](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/protocol-support/tcp/)

В сравнении четырех частных стендов 19 ноября прямой REALITY был ограничен после 90 дней, вариант с посредником в РФ автор остановил сам после 120 дней. Через них прошло 700 и 117 ГБ соответственно. Другие параметры и время также различались. Эти данные не дают причинного доказательства преимущества посредника или рейтинга Беларуси, Армении и Грузии. [Описание стендов](https://habr.com/ru/articles/1109052/)

Второй IPv4 на том же VPS позволяет развести входной и выходной адреса. Проверенный эффект опыта от 24 ноября — смена IP, который видят сайты. Сведения о предотвращении блокировки ограничены, а общий префикс остается общим. Самостоятельный резервный VPS в иной сети хостинга позволяет отдельно проверить отказ основного сервера. [Опыт двух IPv4](https://habr.com/ru/articles/1111468/)

3. **Обратный прокси, альтернативы и границы**

NGINX перед веб-панелью решает задачу HTTP-публикации. Текущий доступ через localhost и SSH уже закрывает прямой внешний путь к форме входа. HTTP-прокси с завершением TLS перед VPN меняет архитектуру транспорта. Для проходящего REALITY применим TCP-проброс. XHTTP допускает разные режимы и промежуточные HTTP-узлы, настройка оценивается как отдельный пилот. [XHTTP](https://github.com/XTLS/Xray-core/discussions/4113)

В исходниках Xray `26.11.9` режим `auto` при REALITY без отдельного `downloadSettings` выбирает `stream-one`. Поэтому смена одного названия режима в такой схеме сохраняет фактический режим передачи. [Код dialer](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L312-L321)

AmneziaWG 3.1 и Hysteria 2 представляют варианты отдельного UDP-резерва. Их пригодность зависит от доступности UDP и конкретного фильтра. `zapret2` применим к ряду ограничений по признакам протокола, его документация отдельно рассматривает ограничения по IP. Для постоянного искусственного фона в 100 Мбит/с подтвержденного преимущества для этой корпоративной схемы в собранных данных нет. [AmneziaWG](https://docs.amnezia.org/ru/documentation/amnezia-wg/), [Hysteria 2](https://v2.hysteria.network/docs/advanced/Full-Client-Config/), [zapret2](https://github.com/bol-van/zapret2)

CDN также требует проверки достижимости. На встрече Tor 19 ноября обсуждалась недоступность части адресов CDN77 для Snowflake из РФ. Исследование InterSecLab отдельно показывает, что приложение может проверять VPN на устройстве. Из этих наблюдений нельзя установить, что конкретный частный VPS был заблокирован из-за приложения. [Tor Project](https://forum.torproject.org/t/tor-project-anti-censorship-team-meeting-notes-2026-11-19/22515), [InterSecLab](https://interseclab.org/max-ru/)

На 4PDA в доступных публикациях встречались разные результаты по операторам и клиентам. Полученные через поисковый индекс фрагменты не содержали воспроизводимого ноябрьского сравнения всех интересовавших стран. Прямой доступ к части тем был ограничен. [Тема собственного VPS](https://4pda.to/forum/index.php?showtopic=1094247&st=4160)

4. **Очередность дальнейших работ**

Сначала фиксируются версии ядра и приложений и собирается контрольная передача данных с каждого используемого подключения. Затем отдельно сравниваются клиентские отпечатки. Обновление сервера проверяется с одним клиентом Windows и актуальным мобильным клиентом. Изменения ключей, SNI и транспорта учитывают уже выданные JSON. После этого можно оценить независимый резерв или мост по результатам обеих трасс. Массовое внедрение и обновление сервера в ноябрьском аудите не выполнялись.
